# DAY 4 — Ansible Templates, Loops, Conditionals and Registers

## 1. Mental model

- **Template:** Render a Jinja2 file using variables and facts, then manage the generated file.
- **Loop:** Repeat one task for each item in a list.
- **Conditional:** Use when to decide whether a task should execute.
- **Register:** Capture a task result so later tasks can inspect it.

Typical workflow: inspect state → register result → evaluate condition → render configuration → validate → notify a handler only when a managed file changes.

## 2. Templates — generate configuration dynamically

A template is a text file containing Jinja2 expressions. The template module renders it on the control node using variables available for the target host, then transfers the result to the managed host.

Example source: templates/app.conf.j2

~~~
# Generated by Ansible. Do not edit manually.
environment={{ app_environment }}
port={{ app_port }}

{% for upstream in app_upstreams %}
upstream={{ upstream }}
{% endfor %}

{% if enable_metrics %}
metrics_enabled=true
{% else %}
metrics_enabled=false
{% endif %}
~~~

Example task:

~~~
- name: Render application configuration
  ansible.builtin.template:
    src: templates/app.conf.j2
    dest: /tmp/ansible-template-lab/app.conf
    mode: "0640"
~~~

The source template normally lives on the control node; dest is the managed-host path. Jinja2 supports variable substitution, loops, conditionals, filters and expressions. The template module compares rendered content with the destination, so stable inputs should not cause changes on every run. Prefer template for complete dynamic configuration and copy for static files. Keep credentials out of templates unless using an approved secrets design.

## 3. Loops — repeat a task for multiple items

~~~
- name: Create application directories
  ansible.builtin.file:
    path: "{{ item }}"
    state: directory
    mode: "0750"
  loop:
    - /tmp/ansible-template-lab/logs
    - /tmp/ansible-template-lab/cache
    - /tmp/ansible-template-lab/data
~~~

The item variable represents the current list element. For a list of dictionaries, access fields such as item.name and item.shell.

~~~
service_accounts:
  - name: appsvc
    shell: /usr/sbin/nologin
  - name: metrics
    shell: /usr/sbin/nologin

- name: Create service accounts
  ansible.builtin.user:
    name: "{{ item.name }}"
    shell: "{{ item.shell }}"
    state: present
  loop: "{{ service_accounts }}"
~~~

Prefer loop for new playbooks; with_items is older syntax. Validate list structure and values, use loop_control.label for readable output, and prefer purpose-built modules over loops of shell commands. A registered result from a loop contains a results list with per-item results.

## 4. Conditionals — control task execution

A when expression is evaluated for each host. Do not wrap the expression in Jinja2 delimiters.

~~~
- name: Install Nginx on Debian-family hosts
  ansible.builtin.package:
    name: nginx
    state: present
  when: ansible_facts['os_family'] == "Debian"
~~~

Multiple conditions in a YAML list mean all conditions must be true:

~~~
when:
  - ansible_facts['os_family'] == "Debian"
  - enable_web_server | bool
~~~

Useful patterns include comparing facts, checking booleans, checking registered return codes, testing whether optional variables are defined, and checking whether lists are non-empty. If a variable is optional, use is defined or a safe default before referencing it. A typo in a when expression can fail the task during condition evaluation.

## 5. Registers — capture task results

register stores the result returned by a task. Depending on the module, fields may include changed, failed, rc, stdout, stderr and module-specific data.

~~~
- name: Check whether the generated configuration exists
  ansible.builtin.stat:
    path: /tmp/ansible-template-lab/app.conf
  register: config_file

- name: Report configuration size
  ansible.builtin.debug:
    msg: "Configuration is {{ config_file.stat.size }} bytes"
  when: config_file.stat.exists
~~~

Command example:

~~~
- name: Read application version
  ansible.builtin.command:
    argv:
      - /usr/bin/printf
      - 1.2.3
  register: app_version
  changed_when: false

- name: Display detected version
  ansible.builtin.debug:
    msg: "Detected version: {{ app_version.stdout }}"
  when: app_version.rc == 0
~~~

register captures output; it does not make a task idempotent. Read-only command checks should normally use changed_when: false. Registered values are runtime data available to later tasks for that host in the play, not a persistent database across runs. A looped task's registered result has a results list.

## 6. Minimal working example

Create a templates directory:

~~~
mkdir -p templates
~~~

Inventory file inventory.ini:

~~~
[local]
localhost ansible_connection=local
~~~

Template file templates/app.conf.j2:

~~~
environment={{ app_environment }}
port={{ app_port }}
{% for upstream in app_upstreams %}
upstream={{ upstream }}
{% endfor %}
{% if enable_metrics %}
metrics_enabled=true
{% else %}
metrics_enabled=false
{% endif %}
~~~

Playbook templates-loops-registers.yml:

~~~
---
- name: Demonstrate templates, loops, conditions and registers
  hosts: local
  gather_facts: true
  vars:
    app_environment: lab
    app_port: 8080
    app_upstreams:
      - 10.0.1.10:8080
      - 10.0.1.11:8080
    enable_metrics: true
    app_directories:
      - /tmp/ansible-template-lab/logs
      - /tmp/ansible-template-lab/cache

  tasks:
    - name: Create application root directory
      ansible.builtin.file:
        path: /tmp/ansible-template-lab
        state: directory
        mode: "0750"

    - name: Create subdirectories using a loop
      ansible.builtin.file:
        path: "{{ item }}"
        state: directory
        mode: "0750"
      loop: "{{ app_directories }}"

    - name: Render application configuration
      ansible.builtin.template:
        src: templates/app.conf.j2
        dest: /tmp/ansible-template-lab/app.conf
        mode: "0640"

    - name: Inspect generated configuration
      ansible.builtin.stat:
        path: /tmp/ansible-template-lab/app.conf
      register: config_file

    - name: Report configuration status
      ansible.builtin.debug:
        msg: "Configuration exists and is {{ config_file.stat.size }} bytes"
      when: config_file.stat.exists

    - name: Read the configured application port
      ansible.builtin.command:
        argv:
          - /usr/bin/grep
          - -E
          - "^port="
          - /tmp/ansible-template-lab/app.conf
      register: port_check
      changed_when: false

    - name: Display the port check result
      ansible.builtin.debug:
        msg: "{{ port_check.stdout }}"
      when: port_check.rc == 0

    - name: Deliberate undefined-variable failure
      ansible.builtin.debug:
        msg: "This task is intentionally broken"
      when: app_prt == 8080
      tags:
        - deliberate_failure
~~~

Run a syntax check and preview targets:

~~~
ansible-playbook -i inventory.ini templates-loops-registers.yml --syntax-check
ansible-playbook -i inventory.ini templates-loops-registers.yml --list-hosts
~~~

Run twice:

~~~
ansible-playbook -i inventory.ini templates-loops-registers.yml
ansible-playbook -i inventory.ini templates-loops-registers.yml
~~~

First run creates directories and renders the file; these tasks may report changed. The stat task registers metadata, and the conditional debug runs because the file exists. The grep task stores rc and stdout in port_check. changed_when: false keeps this read-only check from reporting a change. The second run with unchanged inputs should report changed=0.

Inspect the real file:

~~~
cat /tmp/ansible-template-lab/app.conf
stat /tmp/ansible-template-lab/app.conf
~~~

Expected rendered content:

~~~
environment=lab
port=8080
upstream=10.0.1.10:8080
upstream=10.0.1.11:8080
metrics_enabled=true
~~~

Change app_port to 9090 and run again. The template task should report changed once. Run it again without further changes; it should converge to changed=0.

## 7. Diagnose one deliberate failure with -vvv

Run only the intentionally broken task:

~~~
ansible-playbook -i inventory.ini templates-loops-registers.yml --tags deliberate_failure -vvv
~~~

Ansible reaches localhost using the local connection, then fails while evaluating the when expression because app_prt is undefined. This is a variable-name typo, not an SSH or inventory failure. Verbose output helps identify the selected host, task and evaluation context. Correct app_prt to app_port, rerun, then remove the deliberate-failure task.

## 8. Troubleshooting and production considerations

| Symptom | What to inspect |
|---|---|
| Template fails with undefined variable | Variable spelling, scope, defaults and required inputs |
| Template changes on every run | Timestamps, unstable data, whitespace, ordering or changing source values |
| Loop item fails | Failed item, registered results and input-list structure |
| Conditional skips unexpectedly | Fact/variable value, type, defined status and expression |
| Registered command result is wrong | rc, stdout, stderr, executable path and arguments |
| Read-only command reports changed | Use changed_when: false only if it truly makes no changes |
| Handler does not run | Whether the notifying task reported changed and matched the handler |

Production checklist:
1. Validate required inputs early with ansible.builtin.assert.
2. Use template for complete dynamic configuration files.
3. Validate rendered configuration before reloading a service.
4. Notify a handler only after successful validation.
5. Use handlers for controlled reload/restart operations, not as a substitute for health checks.
6. Protect secrets and avoid exposing them in debug output.
7. Test on a disposable host and verify application behavior after deployment.

## 9. Quick revision

- template = render Jinja2 content using variables and facts.
- loop = repeat a task for each list item; item is the current element.
- when = conditionally execute a task; do not wrap the expression in Jinja2 delimiters.
- register = capture a task result for later tasks.
- changed_when = define whether a task reports changed.
- Run twice with unchanged inputs; verify changed=0 and inspect the actual target state.

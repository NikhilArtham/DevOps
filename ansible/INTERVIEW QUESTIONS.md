# Ansible Interview Questions

Answers are expandable for quick revision. Add new questions here rather than creating separate interview files for each day.

## DAY 1 — Inventory, Ad-hoc Commands and Facts

### 1. What is an Ansible inventory?
<details>
<summary>Answer</summary>

An inventory is the list of managed hosts and groups Ansible can target. It can also define connection details and variables such as SSH user, host address and group-specific settings. Inventory can be static (INI/YAML) or dynamic (generated by an inventory plugin).
</details>

### 2. What is the difference between an inventory hostname and ansible_host?
<details>
<summary>Answer</summary>

The inventory hostname is Ansible's alias for a host, used in patterns and output. `ansible_host` is the actual address Ansible connects to. For example, inventory alias `web01` can connect to `192.0.2.10`.
</details>

### 3. What is an inventory group?
<details>
<summary>Answer</summary>

A group is a logical collection of hosts. A play or ad-hoc command can target the group name, such as `web`, rather than listing each host. Groups can also carry shared variables.
</details>

### 4. What is an Ansible ad-hoc command?
<details>
<summary>Answer</summary>

An ad-hoc command runs a single module against selected inventory hosts without creating a playbook. It is useful for quick checks such as uptime, disk usage or connectivity. Repeatable multi-step configuration is usually better expressed as a playbook.
</details>

### 5. What does the Ansible ping module do? Is it the same as Linux ping?
<details>
<summary>Answer</summary>

No. `ansible.builtin.ping` checks whether Ansible can connect to the managed host and execute its module successfully (for common Linux targets, this involves Python). It does not send ICMP echo packets like the Linux `ping` command.
</details>

### 6. What are Ansible facts?
<details>
<summary>Answer</summary>

Facts are information gathered from managed hosts, such as OS distribution, hostname, interfaces, IP addresses, memory and architecture. They are commonly gathered by the `setup` module and can be referenced in playbooks through `ansible_facts`.
</details>

### 7. How do you gather facts manually?
<details>
<summary>Answer</summary>

Use `ansible all -i inventory.ini -m ansible.builtin.setup`. To reduce output, pass a filter, for example `-a "filter=ansible_distribution*"`. In a playbook, `gather_facts: true` enables automatic gathering at the start of the play.
</details>

### 8. What is the difference between gather_facts: true and false?
<details>
<summary>Answer</summary>

With `gather_facts: true`, Ansible gathers facts before executing the play's tasks (the usual default). With `false`, it skips automatic fact gathering. This can reduce runtime when facts are not needed, but tasks that reference facts must obtain them another way or will fail if those values are unavailable.
</details>

### 9. How do you target one host, a group or all hosts?
<details>
<summary>Answer</summary>

Use an Ansible host pattern: `web01` targets one inventory alias, `web` targets a group, and `all` targets every host in the inventory. Use `--list-hosts` to preview selection before running a potentially disruptive task.
</details>

### 10. What does -vvv do, and how do you use it to troubleshoot?
<details>
<summary>Answer</summary>

It increases Ansible verbosity and exposes more detail about host selection, connection setup, module execution and task results. Use it to distinguish SSH/connectivity problems from remote task failures. Review return code, stdout and stderr, and redact sensitive information before sharing logs.
</details>

### 11. What is the difference between FAILED and UNREACHABLE?
<details>
<summary>Answer</summary>

FAILED generally means Ansible reached the host and executed a task, but the task returned an error. UNREACHABLE means Ansible could not establish or maintain the required connection to the host. Check task stderr/return code for FAILED; check DNS, routing, SSH, credentials and firewall rules for UNREACHABLE.
</details>

### 12. What is idempotency in Ansible?
<details>
<summary>Answer</summary>

Idempotency means applying the same desired state repeatedly results in no additional changes after convergence. For example, a file task with `state: directory` ensures a directory exists; after the first successful creation, another run should report no change if the desired state is unchanged. A successful run alone does not prove idempotency: run it twice and compare the recap.
</details>

### 13. Why should you prefer command over shell when possible?
<details>
<summary>Answer</summary>

The command module executes a command without invoking a shell, reducing shell interpretation and quoting risks. Use shell only when you need shell features such as pipes, redirects, globbing or variable expansion. Prefer purpose-built Ansible modules for configuration because they can express desired state and support idempotency.
</details>

### 14. How do you troubleshoot a host that is not reachable through Ansible?
<details>
<summary>Answer</summary>

First confirm inventory selection with `ansible-inventory --graph` and `--list-hosts`. Then verify the host address, DNS, route, SSH port, SSH service, username, key path and key permissions. Run the ping module with `-vvv` and compare with a direct SSH attempt from the control node. Check firewall/security-group rules and whether the managed host has the required Python interpreter.
</details>

### 15. Can facts become stale?
<details>
<summary>Answer</summary>

Yes. If fact caching is configured, Ansible may reuse cached values until they expire or are refreshed. Even freshly gathered facts describe the host at gather time and can become outdated after changes during a long-running workflow. Understand the play's fact-gathering and cache configuration before relying on a value.
</details>


## DAY 2 — Variables and Precedence

### 16. Why are variables used in Ansible?
<details>
<summary>Answer</summary>

Variables make automation reusable and configurable. The same playbook can deploy to development, QA and production by changing inventory or variable inputs instead of maintaining separate copies of the playbook.
</details>

### 17. What is variable precedence in Ansible?
<details>
<summary>Answer</summary>

Variable precedence is the rule Ansible uses when the same variable is defined in multiple sources. The source with higher precedence determines the effective value. Extra vars passed with `-e` have the highest variable precedence.
</details>

### 18. What is the difference between group_vars and host_vars?
<details>
<summary>Answer</summary>

`group_vars` defines values shared by hosts in an inventory group. `host_vars` defines values for a specific inventory host. Host-specific values normally override group values when both define the same variable.
</details>

### 19. Which takes precedence: group vars or host vars?
<details>
<summary>Answer</summary>

For the common inventory variable sources, host variables take precedence over group variables. Group hierarchy and merge ordering also matter when multiple groups apply to a host.
</details>

### 20. Which takes precedence: play vars or task vars?
<details>
<summary>Answer</summary>

Task-level variables have higher precedence than play-level variables for the task where they are defined. Their scope is limited to that task; they do not permanently rewrite the play variable.
</details>

### 21. What is the highest-precedence variable source?
<details>
<summary>Answer</summary>

Extra variables supplied at runtime, commonly through `-e` or `--extra-vars`, have the highest variable precedence. For example, `ansible-playbook site.yml -e "app_port=9090"` overrides ordinary inventory and play/task variable definitions.
</details>

### 22. What is the difference between vars and vars_files?
<details>
<summary>Answer</summary>

`vars` defines variables inline in a play, role or supported block/task scope. `vars_files` loads variables from one or more external YAML files. External files can help organize environment-specific or larger sets of configuration values.
</details>

### 23. Does ansible-inventory --host show the final effective variable value?
<details>
<summary>Answer</summary>

No. It displays inventory-derived host variables. It does not evaluate every runtime source such as play vars, task vars, role context, registered values or extra vars. Use a debug task in the actual play to inspect the value in that execution scope.
</details>

### 24. What happens when the same variable is defined in group_vars and host_vars?
<details>
<summary>Answer</summary>

The host-specific value normally overrides the group value for that host. This is useful when most servers share a common setting but one host needs a deliberate exception.
</details>

### 25. What is the purpose of role defaults?
<details>
<summary>Answer</summary>

Role defaults provide low-precedence default values for a role. They are designed to be easily overridden by inventory, play or other higher-precedence inputs. Put sensible configurable defaults in `defaults/main.yml`.
</details>

### 26. What is set_fact?
<details>
<summary>Answer</summary>

`ansible.builtin.set_fact` creates or updates a variable associated with the current host during play execution. It is useful for deriving values from facts or task results. Its precedence is higher than many ordinary variable sources, and fact caching can affect later runs if configured.
</details>

### 27. How do you troubleshoot an unexpected variable value?
<details>
<summary>Answer</summary>

Search for every definition of the variable, inspect group membership and host vars, review play/task/role scope, check included variable files and registered/set_fact values, and inspect command-line extra vars. Use `ansible-inventory --host` for inventory values and a debug task to print the runtime value in the relevant scope.
</details>

### 28. How do you pass a variable from the command line?
<details>
<summary>Answer</summary>

Use `-e` or `--extra-vars`, for example `ansible-playbook -i inventory.ini site.yml -e "app_port=9090"`. For structured values, JSON or a YAML/JSON variable file can be passed. Avoid putting passwords or tokens directly on command lines because they may be exposed through shell history or process inspection.
</details>

### 29. How can you prevent a playbook from running with a missing required variable?
<details>
<summary>Answer</summary>

Validate required inputs early using `ansible.builtin.assert`, role argument specifications, or explicit variable validation. Provide a clear failure message that explains which variable is missing and what valid values are expected.
</details>

### 30. How do you keep secrets in Ansible variables secure?
<details>
<summary>Answer</summary>

Use Ansible Vault or an approved secrets manager rather than committing plaintext credentials. Restrict access to vault passwords and secret files, and use `no_log: true` on tasks whose output may expose sensitive values. `no_log` reduces log exposure; it does not encrypt the variable source or every copy of the secret.
</details>


## DAY 3 — Playbooks, idempotency and handlers

### 31. What is an Ansible playbook?
<details>
<summary>Answer</summary>

A playbook is a YAML file containing one or more plays. Each play targets a set of inventory hosts and defines tasks, variables, privilege escalation, handlers and other execution behavior. Playbooks are used for repeatable multi-step automation.
</details>

### 32. What is the difference between a play and a task?
<details>
<summary>Answer</summary>

A play maps a host pattern to a set of tasks and execution settings. A task is one operation within that play, usually invoking an Ansible module on the selected hosts.
</details>

### 33. What is idempotency in Ansible?
<details>
<summary>Answer</summary>

Idempotency means repeated execution with the same inputs converges on the same desired state without making additional changes after convergence. For example, a file module ensuring a directory exists should report changed when it creates the directory and ok on a subsequent unchanged run.
</details>

### 34. How do you verify that a playbook is idempotent?
<details>
<summary>Answer</summary>

Run the playbook twice against the same hosts with unchanged inputs. Inspect the recap and task results. The first run may report changed while creating or correcting resources; the second run should normally report changed=0. Also verify the actual application/service state, not just the recap.
</details>

### 35. What is an Ansible handler?
<details>
<summary>Answer</summary>

A handler is a special task that runs when notified by another task that reports changed. Handlers are commonly used for service reloads or restarts after configuration changes, avoiding unnecessary service actions on every playbook run.
</details>

### 36. When does a handler execute?
<details>
<summary>Answer</summary>

A notified handler normally runs at the end of the play, after the ordinary tasks have completed. It can be triggered earlier with `ansible.builtin.meta: flush_handlers`.
</details>

### 37. Does a task notify a handler when it reports ok?
<details>
<summary>Answer</summary>

No. A task must report changed for its notification to trigger. If the managed resource is already in the desired state, the task reports ok and the handler is not notified.
</details>

### 38. What happens if multiple tasks notify the same handler?
<details>
<summary>Answer</summary>

The handler normally runs once at the end of that play, even if several tasks notify it. This prevents repeated restarts when multiple configuration files change in the same play.
</details>

### 39. What is the difference between a handler and a normal task?
<details>
<summary>Answer</summary>

A normal task runs when Ansible reaches it in the task sequence, subject to conditions and execution controls. A handler is event-driven: it runs only when notified by a changed task, and normally runs later at the end of the play.
</details>

### 40. What is the difference between service state started, restarted and reloaded?
<details>
<summary>Answer</summary>

`started` ensures a service is running and is idempotent. `restarted` performs a stop/start operation. `reloaded` asks the service to reload its configuration without a full restart when supported. Choose based on the service's capabilities and the change being applied.
</details>

### 41. What is notify in Ansible?
<details>
<summary>Answer</summary>

`notify` links a task to a handler by name or listen topic. If the task reports changed, Ansible queues the matching handler for execution. If the task reports ok, it does not notify the handler.
</details>

### 42. What is meta: flush_handlers?
<details>
<summary>Answer</summary>

`ansible.builtin.meta: flush_handlers` runs all handlers notified so far at that point in the play rather than waiting until the normal end-of-play handler phase. Later tasks can notify those handlers again.
</details>

### 43. What does force_handlers do?
<details>
<summary>Answer</summary>

`force_handlers: true` tells Ansible to run notified handlers even if a later task fails on that host, subject to the host still being reachable and other execution constraints. Use it carefully because the handler may restart or reload a service while the deployment is only partially complete.
</details>

### 44. Why might an Ansible task report changed on every run?
<details>
<summary>Answer</summary>

The task may use a non-idempotent shell/command, append duplicate content, include a changing timestamp, render unstable template data, or continually correct permissions/content. Inspect the task diff and use a state-aware module such as copy, template, file, package or service where possible.
</details>

### 45. How do you troubleshoot a handler that does not run?
<details>
<summary>Answer</summary>

Check whether the notifying task actually reported changed, whether the notify name matches the handler name or listen topic, whether the handler is in the same play, and whether execution reached the handler phase. Also inspect task conditions, tags, failures and handler flushing behavior.
</details>


## DAY 4 — Templates, loops, conditionals and registers

### 46. What is an Ansible template?
<details>
<summary>Answer</summary>

A template is a text file processed with Jinja2 expressions. The ansible.builtin.template module renders it using variables and facts, then manages the resulting file on the target host. It is commonly used for dynamic application, proxy and service configuration.
</details>

### 47. What is the difference between copy and template?
<details>
<summary>Answer</summary>

The copy module transfers a file without rendering Jinja2 variables. The template module renders a Jinja2 source file on the control node and transfers the generated content. Use copy for static files and template for files whose content depends on variables or facts.
</details>

### 48. Where is a Jinja2 template rendered?
<details>
<summary>Answer</summary>

The template is rendered on the Ansible control node using variables and facts available for the target host. The rendered file is then transferred to the managed host.
</details>

### 49. What is a loop in Ansible?
<details>
<summary>Answer</summary>

A loop repeats a task for each element in a list. The current element is available through the item variable by default. It avoids duplicating nearly identical tasks, such as creating several directories or users.
</details>

### 50. What is the difference between loop and with_items?
<details>
<summary>Answer</summary>

loop is the recommended modern syntax for iterating over a list. with_items is older loop syntax and may have different historical flattening behavior. Prefer loop for new playbooks unless a specific lookup-based with_* construct is needed.
</details>

### 51. How do you access fields in a loop over dictionaries?
<details>
<summary>Answer</summary>

Use expressions such as item.name or item.shell when each list element is a dictionary. A list of account dictionaries can drive one user task with name set from item.name.
</details>

### 52. What is a conditional in Ansible?
<details>
<summary>Answer</summary>

A conditional controls whether a task, block or play should execute. The when keyword evaluates an expression for each target host. It is often used with facts, variables, registered results and boolean flags.
</details>

### 53. Should a when expression be wrapped in Jinja2 delimiters?
<details>
<summary>Answer</summary>

No. Write the expression directly, for example when: ansible_facts['os_family'] == "Debian". Do not wrap the expression in Jinja2 delimiters; Ansible evaluates the conditional expression itself.
</details>

### 54. How do you combine multiple conditions?
<details>
<summary>Answer</summary>

Use a YAML list under when for AND behavior: every condition must be true. For OR behavior, use an expression with or or a suitable list-membership test. Keep complex conditions readable and validate optional variables before referencing them.
</details>

### 55. What is register in Ansible?
<details>
<summary>Answer</summary>

register stores the result returned by a task in a variable. Later tasks can inspect fields such as rc, stdout, stderr, changed, failed or module-specific result data. The registered result is runtime data associated with that host and play execution.
</details>

### 56. What fields are commonly available in a registered command result?
<details>
<summary>Answer</summary>

Common fields include rc for the return code, stdout and stderr for output streams, and status fields such as changed and failed. Exact fields can vary by module. Use a debug task in a safe lab to inspect the structure.
</details>

### 57. Does register make a command idempotent?
<details>
<summary>Answer</summary>

No. Register only captures the task result. It does not change how the task behaves. A read-only command can be marked with changed_when: false; a command that changes the system still needs an idempotent design or a purpose-built module.
</details>

### 58. What is changed_when used for?
<details>
<summary>Answer</summary>

changed_when defines the condition under which a task should report changed. It is useful when a command module cannot infer whether a change occurred. For a genuinely read-only diagnostic command, changed_when: false prevents a misleading changed result.
</details>

### 59. What happens when a registered task is inside a loop?
<details>
<summary>Answer</summary>

The registered result generally contains a results list with an entry for each loop item, rather than only one flat task result. Each item result can include its own item value and module return fields. Inspect the structure before writing conditions against loop results.
</details>

### 60. How do you troubleshoot a task skipped because of a when condition?
<details>
<summary>Answer</summary>

Print the variables, facts or registered result used by the condition. Confirm the variable is defined, check its actual type and value, and verify the expression's comparison or boolean conversion. Use verbosity for task context, but a targeted debug task is often the clearest way to inspect condition inputs.
</details>


## DAY 5 — Roles and reusable structure

### 61. What is an Ansible role?
<details>
<summary>Answer</summary>

A role is a reusable, structured collection of related automation content such as tasks, handlers, templates, static files, variables and metadata. It helps organize playbooks, reduce duplication and share automation across environments or projects.
</details>

### 62. What is the purpose of the tasks directory in a role?
<details>
<summary>Answer</summary>

The tasks directory contains the role's task files. tasks/main.yml is the default entry point that Ansible executes when the role is invoked. It can import or include additional task files.
</details>

### 63. What is the difference between defaults/main.yml and vars/main.yml?
<details>
<summary>Answer</summary>

defaults/main.yml contains low-precedence role defaults intended to be overridden by inventory or play inputs. vars/main.yml contains role variables with substantially higher precedence. Put normal user-configurable settings in defaults; reserve vars for values that should be harder to override.
</details>

### 64. What is the purpose of handlers/main.yml in a role?
<details>
<summary>Answer</summary>

It defines handlers that can be notified by tasks in the role. A handler normally runs only when a notifying task reports changed, and usually executes at the end of the play. A common example is reloading a service after a configuration file changes.
</details>

### 65. What is the difference between files and templates in a role?
<details>
<summary>Answer</summary>

The files directory holds static files copied to managed hosts without Jinja2 rendering. The templates directory holds Jinja2 source files rendered using variables and facts before being transferred.
</details>

### 66. How do you create an Ansible role?
<details>
<summary>Answer</summary>

Use ansible-galaxy role init role_name to generate the standard role skeleton. For a project-local role, run it inside the project's roles directory. You can also create only the directories needed by a small role manually.
</details>

### 67. How does Ansible find a project-local role?
<details>
<summary>Answer</summary>

Ansible searches configured role paths. A conventional project layout places a roles directory alongside the playbook. Inspect configured search paths with ansible-config dump and the DEFAULT_ROLES_PATH setting.
</details>

### 68. How do you call a role from a playbook?
<details>
<summary>Answer</summary>

A role can be listed under a play's roles section, or invoked as a task using ansible.builtin.import_role or ansible.builtin.include_role. Choose based on whether static parsing or dynamic runtime inclusion is required.
</details>

### 69. What is the difference between import_role and include_role?
<details>
<summary>Answer</summary>

import_role is static: Ansible processes the role during playbook parsing. include_role is dynamic: Ansible loads the role during execution. Dynamic inclusion is useful for runtime conditions and loops, while static imports make tasks available to parsing-time features. Tag and condition inheritance can differ, so test the intended behavior.
</details>

### 70. Can one role be reused for development, QA and production?
<details>
<summary>Answer</summary>

Yes. Keep environment-independent logic in the role and expose configurable values through role defaults. Supply different values through inventory group/host variables or play-level role parameters. Avoid copying the role for every environment unless the actual behavior differs.
</details>

### 71. Why should a role be focused on one responsibility?
<details>
<summary>Answer</summary>

A focused role is easier to test, review, reuse and troubleshoot. For example, an Nginx role should manage Nginx rather than also owning unrelated database, monitoring and user-provisioning workflows. Larger deployments can compose several focused roles.
</details>

### 72. How do you pass variables to a role?
<details>
<summary>Answer</summary>

Define role defaults and override them through inventory variables, play variables or variables supplied alongside a role invocation under roles. You can also pass variables when using import_role or include_role. Variable precedence differs by source and invocation style.
</details>

### 73. What is meta/main.yml used for?
<details>
<summary>Answer</summary>

It contains role metadata such as author, description, supported platforms, dependencies and other Galaxy-related information. It helps document and distribute a role and can declare role dependencies where appropriate.
</details>

### 74. How do you test a role independently?
<details>
<summary>Answer</summary>

Create a small test playbook and inventory that invoke only the role, validate its inputs, run it against disposable hosts, and execute it twice to check idempotency. For mature roles, use a role-testing framework such as Molecule where appropriate.
</details>

### 75. What makes an Ansible role production-ready?
<details>
<summary>Answer</summary>

A production-ready role has a focused responsibility, documented inputs and defaults, validated variables, idempotent tasks, safe handlers, supported-platform assumptions, secret handling, failure behavior and repeatable tests. It should be reusable without hardcoded environment-specific values or hidden dependencies.
</details>


## DAY 6 — Vault and secret handling

### 76. What is Ansible Vault?
<details>
<summary>Answer</summary>

Ansible Vault encrypts sensitive data such as variable files or individual strings so the plaintext is not stored in the repository. Ansible decrypts the data when it is needed during playbook execution and an authorized Vault password is supplied. Vault protects data at rest; it does not automatically prevent runtime output or target-host exposure.
</details>

### 77. How do you encrypt and inspect a variable file?
<details>
<summary>Answer</summary>

Use `ansible-vault encrypt group_vars/all/vault.yml` to encrypt a file. `ansible-vault view` displays its decrypted content, so use it only in a safe terminal. The encrypted file begins with an Ansible Vault header. Avoid copying decrypted output into logs or tickets.
</details>

### 78. What is the difference between ansible-vault encrypt and encrypt_string?
<details>
<summary>Answer</summary>

`ansible-vault encrypt` encrypts an entire file in place. `ansible-vault encrypt_string` encrypts one value and prints an encrypted YAML-compatible string that can be embedded in a variable file. Both require secure handling of the Vault password and generated output.
</details>

### 79. How do you run a playbook that uses Vault-encrypted variables?
<details>
<summary>Answer</summary>

For an interactive prompt, use `ansible-playbook site.yml --ask-vault-pass`. You can also use a protected password file or a named Vault ID with `--vault-id`. In CI/CD, retrieve the password from an approved protected secret store rather than hardcoding it in source code.
</details>

### 80. What is a Vault ID?
<details>
<summary>Answer</summary>

A Vault ID is a label associated with a Vault password, such as dev, qa or prod. It helps Ansible select the appropriate password when multiple encrypted files use different passwords. A Vault ID is only a label; it does not itself enforce access permissions.
</details>

### 81. What is no_log in Ansible?
<details>
<summary>Answer</summary>

`no_log: true` suppresses sensitive task arguments and results from normal Ansible output. Use it on tasks that handle passwords, tokens or secret-bearing results. It does not encrypt variables, protect the destination file, or guarantee that every external callback or application log is safe.
</details>

### 82. Does Ansible Vault prevent a secret from appearing in task output?
<details>
<summary>Answer</summary>

No. Vault encrypts data at rest and Ansible decrypts it for runtime use. A debug task or another task can still print the decrypted value. Avoid debugging secrets and use `no_log: true` for tasks whose arguments or results are sensitive.
</details>

### 83. What is the difference between Vault and no_log?
<details>
<summary>Answer</summary>

Vault encrypts secret source data at rest, such as a YAML variable file committed to Git. `no_log` suppresses task details in Ansible output. They address different exposure paths and are often used together.
</details>

### 84. How should Vault passwords be handled in CI/CD?
<details>
<summary>Answer</summary>

Store the Vault password in an approved CI secret store or external secrets manager, restrict access to authorized workflows and branches, and retrieve it only at runtime. Do not hardcode it in playbooks, repository files, container images or pipeline YAML. Avoid shell tracing and ensure logs and artifacts do not expose it.
</details>

### 85. Is a Vault password file safe to commit if the Vault data is encrypted?
<details>
<summary>Answer</summary>

No. Anyone with both the encrypted file and the password can decrypt the secrets. A password file must be stored separately, protected with restrictive permissions and excluded from Git and artifacts. For local learning, an interactive prompt is safer and simpler.
</details>

### 86. How do you rotate a Vault password?
<details>
<summary>Answer</summary>

Use `ansible-vault rekey encrypted_file.yml` to change the password protecting an encrypted file. Coordinate the change with authorized users and CI systems, update the protected password store, and verify that the intended workflows can decrypt the file. Credential rotation inside the application is a separate operation.
</details>

### 87. What happens if a Vault-encrypted variable is undefined at runtime?
<details>
<summary>Answer</summary>

Ansible may not have loaded the file or variable at all. Check the `group_vars` or `host_vars` path, inventory group membership, explicit `vars_files`, YAML structure and variable spelling. A missing variable is different from a decryption failure, which indicates Ansible could not decrypt the encrypted data.
</details>

### 88. Does no_log make verbose output completely safe?
<details>
<summary>Answer</summary>

No. It suppresses details for the task where it is configured, but other tasks, callbacks, external tools, shell tracing or application logs may still expose secrets. Review output before sharing it and avoid printing secrets in the first place. Verbosity is a diagnostic aid, not a security control.
</details>

### 89. How should secret-bearing files be protected on managed hosts?
<details>
<summary>Answer</summary>

Use restrictive ownership and permissions, such as owner-only read/write mode 0600 when appropriate. Limit access to the service identity that needs the file, consider backups and temporary copies, and rotate the credential if exposure is suspected. Vault does not encrypt the deployed file automatically.
</details>

### 90. What should you do if a secret is accidentally committed to Git?
<details>
<summary>Answer</summary>

Treat the secret as compromised: revoke or rotate it immediately, investigate access and usage, and remove or rewrite exposed history according to the organization's incident process. Deleting the file in a later commit does not remove the secret from earlier Git history, forks, clones or cached artifacts.
</details>


## DAY 7 — Troubleshooting and verbose execution

### 91. What is your systematic approach to troubleshooting an Ansible playbook?
<details>
<summary>Answer</summary>

Start by confirming inventory and host selection, then validate syntax, connectivity and privilege escalation. Identify the first failing task, inspect the module result and return code, check relevant variables and target state, fix the root cause, rerun the narrowest safe test and independently verify the application outcome.
</details>

### 92. What do -v, -vv, -vvv and -vvvv do?
<details>
<summary>Answer</summary>

They progressively increase Ansible verbosity. Use -v for additional task details, -vv for more execution information, -vvv for detailed connection/module troubleshooting and -vvvv for very detailed connection/plugin debugging. Use the lowest level that provides enough evidence.
</details>

### 93. How do you verify which hosts a playbook will target?
<details>
<summary>Answer</summary>

Use `ansible-playbook -i inventory.ini site.yml --list-hosts` to preview selected hosts. Use `ansible-inventory -i inventory.ini --graph` to inspect group structure. This catches many inventory and host-pattern mistakes before tasks run.
</details>

### 94. What is the difference between Ansible ping and ICMP ping?
<details>
<summary>Answer</summary>

The `ansible.builtin.ping` module checks whether Ansible can connect to a managed host and execute a small module, generally over the configured connection such as SSH. The operating-system ping command sends ICMP echo requests. One can work while the other is blocked.
</details>

### 95. What does UNREACHABLE mean?
<details>
<summary>Answer</summary>

Ansible could not establish or use the configured connection to the host. Check the hostname/IP, DNS, route, port, firewall, SSH service, remote username, authentication method and connection variables. It is different from a task that connected successfully and then failed.
</details>

### 96. How do you troubleshoot a task that fails with a non-zero return code?
<details>
<summary>Answer</summary>

Identify the exact task and command, inspect the registered result fields such as rc, stdout and stderr, and compare the command's behavior with its intended success condition. A non-zero rc does not always include stderr. Do not override failed_when until the command's return semantics are understood.
</details>

### 97. What is the purpose of --syntax-check?
<details>
<summary>Answer</summary>

It checks playbook syntax and structure without executing the tasks. It can catch YAML and playbook parsing problems, but it does not prove remote connectivity, runtime variable availability, module success or application health.
</details>

### 98. How do you debug an undefined variable?
<details>
<summary>Answer</summary>

Check spelling, variable scope, inventory group/host membership, vars_files and whether the relevant file is loaded. Use a safe assert or a debug statement for non-sensitive values. Never print passwords or tokens to diagnose variable loading.
</details>

### 99. What is --start-at-task used for?
<details>
<summary>Answer</summary>

It starts playbook execution at a task with the specified name. It is useful for focused debugging, but earlier tasks are skipped. Use it only when required prerequisites and state are already present; otherwise the resumed task may fail for reasons caused by skipped setup.
</details>

### 100. What is --step used for?
<details>
<summary>Answer</summary>

It makes Ansible ask for confirmation before each task, allowing an operator to inspect and control execution interactively. It is useful for controlled debugging but is unsuitable for unattended automation and can be risky if task effects are not understood.
</details>

### 101. What is the purpose of --limit?
<details>
<summary>Answer</summary>

It restricts execution to a subset of hosts matching the supplied pattern. It is useful for canary or targeted troubleshooting. Confirm the resulting host set first and remember that limiting hosts can affect dependencies and orchestration assumptions.
</details>

### 102. What is Ansible check mode?
<details>
<summary>Answer</summary>

Check mode, enabled with `--check`, asks supported modules to predict changes without applying them. Module support varies, and commands or custom modules may not provide reliable predictions. It is a useful preview, not a replacement for testing in a safe environment.
</details>

### 103. What is the difference between changed_when and failed_when?
<details>
<summary>Answer</summary>

`changed_when` controls whether Ansible reports a task as changed. `failed_when` controls whether the task result is treated as a failure. They are useful for commands whose return codes do not match Ansible's default assumptions, but incorrect conditions can hide failures or create false change reports.
</details>

### 104. Why can a playbook succeed while the application is still unavailable?
<details>
<summary>Answer</summary>

Ansible reports task execution outcomes, not necessarily end-user application health. A service may be running but have invalid configuration, failed dependencies, bad routing or an unhealthy backend. Add configuration validation, service checks and application-level health tests after deployment.
</details>

### 105. Is -vvvv output safe to share?
<details>
<summary>Answer</summary>

Not automatically. It can expose hostnames, usernames, file paths, connection details and command arguments. Secret-bearing tasks should use `no_log: true`, but this does not sanitize every callback, external command or application log. Review and redact output before sharing it.
</details>



## DAY 8 — Automating AWS configuration with Ansible + SSM

### 106. What is the purpose of the amazon.aws.aws_ssm connection plugin?
<details>
<summary>Answer</summary>

It allows Ansible to execute tasks on an EC2 instance through an AWS Systems Manager session rather than using SSH as the transport. Ansible remains the configuration-management engine; SSM provides the connection path.
</details>

### 107. Does using SSM mean the EC2 instance needs no network connectivity?
<details>
<summary>Answer</summary>

No. The SSM Agent needs outbound connectivity to the regional Systems Manager endpoints, typically over HTTPS TCP 443. The instance also needs access to S3 for file transfers performed by the Ansible SSM connection plugin. Private instances can use NAT or the appropriate VPC endpoints.
</details>

### 108. What must be installed on the Ansible controller to use the SSM connection?
<details>
<summary>Answer</summary>

Install the `amazon.aws` collection, the AWS Session Manager Plugin binary, and compatible AWS SDK dependencies such as boto3 and botocore as required. Configure an AWS identity with the necessary SSM and S3 permissions.
</details>

### 109. What IAM permissions does the EC2 instance need for Systems Manager?
<details>
<summary>Answer</summary>

The instance needs an IAM instance profile with permissions that allow SSM Agent to register and communicate with Systems Manager. The AWS-managed `AmazonSSMManagedInstanceCore` policy is a common baseline. Additional permissions should be added only for the actual workload.
</details>

### 110. What is the role of the S3 bucket in amazon.aws.aws_ssm?
<details>
<summary>Answer</summary>

The connection plugin stages Ansible module files and data through S3. This is required even for command or shell tasks because the module code must reach the target. The controller needs appropriate bucket/object permissions, and the target needs network access to S3 to transfer files using presigned URLs.
</details>

### 111. Why can S3 be a security concern when using the Ansible SSM connection?
<details>
<summary>Answer</summary>

Files transferred through the plugin may contain task data. The plugin attempts to delete objects after a run, but interrupted runs can leave objects behind and bucket versioning can preserve deleted object versions. The plugin documentation warns that secret-bearing transferred files can remain in S3 version history in plaintext. Avoid transferring secrets through this path unless the exposure has been explicitly assessed and controlled.
</details>

### 112. Does Ansible over SSM require inbound TCP 22?
<details>
<summary>Answer</summary>

No. The SSM connection does not require the controller to SSH into the instance, so inbound SSH can remain closed. The instance still needs outbound connectivity to Systems Manager and S3, and the controller needs access to the AWS APIs and staging bucket.
</details>

### 113. How do you configure a static inventory host for SSM?
<details>
<summary>Answer</summary>

Use the EC2 instance ID as the inventory hostname and define connection variables such as `ansible_connection=amazon.aws.aws_ssm`, `ansible_aws_ssm_region` and `ansible_aws_ssm_bucket_name`. Keep credentials outside the inventory and use an approved AWS profile or assumed role on the controller.
</details>

### 114. What is the difference between the SSM connection plugin and an SSM Run Command module?
<details>
<summary>Answer</summary>

The SSM connection plugin provides a transport so normal Ansible tasks and modules can execute on an EC2 managed node. An SSM Run Command module invokes an AWS Systems Manager command operation as an AWS API action. They are different execution models.
</details>

### 115. What should you check if an EC2 instance is not visible as a managed node?
<details>
<summary>Answer</summary>

Check that SSM Agent is installed and running, the instance profile is attached and has required permissions, the Region is correct, and the instance can reach Systems Manager endpoints over outbound HTTPS. For private instances inspect VPC endpoints or NAT, DNS, routes, endpoint policies and security groups.
</details>

### 116. What should you check if Session Manager works in the AWS console but Ansible fails?
<details>
<summary>Answer</summary>

Check that the controller has the amazon.aws collection, Session Manager Plugin and compatible boto3/botocore dependencies. Verify the AWS identity, Region, SSM session permissions, S3 bucket name and S3 permissions. Console access working does not prove that the controller has all plugin prerequisites.
</details>

### 117. Why does the SSM connection plugin require curl on a Linux managed node?
<details>
<summary>Answer</summary>

The plugin uses presigned S3 URLs to transfer files between the controller and the managed instance. The Linux target uses curl to download or upload those files. Network access to the bucket is therefore required.
</details>

### 118. How do you troubleshoot an S3 AccessDenied error during an SSM Ansible run?
<details>
<summary>Answer</summary>

Confirm the controller's AWS identity and check its S3 bucket and object permissions, bucket policy, object prefix, Region and any KMS key policy if SSE-KMS is used. Also confirm the configured bucket is the intended staging bucket and that public access has not been opened as a workaround.
</details>

### 119. Does the SSM connection plugin support ansible_user or remote_user like SSH?
<details>
<summary>Answer</summary>

The plugin documentation states that `ansible_user` and `remote_user` do not configure the remote user in the same way as SSH. The session often runs as the SSM agent's configured operating-system user. Use a supported SSM Session document for run-as behavior or Ansible privilege escalation with `become_user` where appropriate.
</details>

### 120. How would you design Ansible + SSM for a private EC2 fleet in production?
<details>
<summary>Answer</summary>

Use dynamic EC2 inventory filtered by account, Region and tags; instance profiles with least-privilege SSM permissions; private connectivity through required VPC endpoints; a dedicated protected S3 staging bucket; and a controller role with scoped SSM/S3 access. Pin collection versions, avoid transferring secrets through S3, use canary batches, validate application health and audit session activity.
</details>

# Ansible Interview Questions

## DAY 1 — Inventory, Ad-hoc Commands and Facts

### 1. What is an Ansible inventory?
<details>
<summary>Answer</summary>

An inventory is the list of managed hosts and groups Ansible can target. It can also define connection details and variables such as SSH user, host address and group-specific settings. Inventory can be static (INI/YAML) or dynamic (generated by an inventory plugin).
</details>

### 2. What is the difference between an inventory hostname and ansible_host?
<details>
<summary>Answer</summary>

The inventory hostname is Ansible's alias for a host, used in patterns and output. `ansible_host` is the actual address Ansible connects to. For example, inventory alias `web01` can connect to `192.0.2.10`.
</details>

### 3. What is an inventory group?
<details>
<summary>Answer</summary>

A group is a logical collection of hosts. A play or ad-hoc command can target the group name, such as `web`, rather than listing each host. Groups can also carry shared variables.
</details>

### 4. What is an Ansible ad-hoc command?
<details>
<summary>Answer</summary>

An ad-hoc command runs a single module against selected inventory hosts without creating a playbook. It is useful for quick checks such as uptime, disk usage or connectivity. Repeatable multi-step configuration is usually better expressed as a playbook.
</details>

### 5. What does the Ansible ping module do? Is it the same as Linux ping?
<details>
<summary>Answer</summary>

No. `ansible.builtin.ping` checks whether Ansible can connect to the managed host and execute its module successfully (for common Linux targets, this involves Python). It does not send ICMP echo packets like the Linux `ping` command.
</details>

### 6. What are Ansible facts?
<details>
<summary>Answer</summary>

Facts are information gathered from managed hosts, such as OS distribution, hostname, interfaces, IP addresses, memory and architecture. They are commonly gathered by the `setup` module and can be referenced in playbooks through `ansible_facts`.
</details>

### 7. How do you gather facts manually?
<details>
<summary>Answer</summary>

Use `ansible all -i inventory.ini -m ansible.builtin.setup`. To reduce output, pass a filter, for example `-a "filter=ansible_distribution*"`. In a playbook, `gather_facts: true` enables automatic gathering at the start of the play.
</details>

### 8. What is the difference between gather_facts: true and false?
<details>
<summary>Answer</summary>

With `gather_facts: true`, Ansible gathers facts before executing the play's tasks (the usual default). With `false`, it skips automatic fact gathering. This can reduce runtime when facts are not needed, but tasks that reference facts must obtain them another way or will fail if those values are unavailable.
</details>

### 9. How do you target one host, a group or all hosts?
<details>
<summary>Answer</summary>

Use an Ansible host pattern: `web01` targets one inventory alias, `web` targets a group, and `all` targets every host in the inventory. Use `--list-hosts` to preview selection before running a potentially disruptive task.
</details>

### 10. What does -vvv do, and how do you use it to troubleshoot?
<details>
<summary>Answer</summary>

It increases Ansible verbosity and exposes more detail about host selection, connection setup, module execution and task results. Use it to distinguish SSH/connectivity problems from remote task failures. Review return code, stdout and stderr, and redact sensitive information before sharing logs.
</details>

### 11. What is the difference between FAILED and UNREACHABLE?
<details>
<summary>Answer</summary>

FAILED generally means Ansible reached the host and executed a task, but the task returned an error. UNREACHABLE means Ansible could not establish or maintain the required connection to the host. Check task stderr/return code for FAILED; check DNS, routing, SSH, credentials and firewall rules for UNREACHABLE.
</details>

### 12. What is idempotency in Ansible?
<details>
<summary>Answer</summary>

Idempotency means applying the same desired state repeatedly results in no additional changes after convergence. For example, a file task with `state: directory` ensures a directory exists; after the first successful creation, another run should report no change if the desired state is unchanged. A successful run alone does not prove idempotency: run it twice and compare the recap.
</details>

### 13. Why should you prefer command over shell when possible?
<details>
<summary>Answer</summary>

The command module executes a command without invoking a shell, reducing shell interpretation and quoting risks. Use shell only when you need shell features such as pipes, redirects, globbing or variable expansion. Prefer purpose-built Ansible modules for configuration because they can express desired state and support idempotency.
</details>

### 14. How do you troubleshoot a host that is not reachable through Ansible?
<details>
<summary>Answer</summary>

First confirm inventory selection with `ansible-inventory --graph` and `--list-hosts`. Then verify the host address, DNS, route, SSH port, SSH service, username, key path and key permissions. Run the ping module with `-vvv` and compare with a direct SSH attempt from the control node. Check firewall/security-group rules and whether the managed host has the required Python interpreter.
</details>

### 15. Can facts become stale?
<details>
<summary>Answer</summary>

Yes. If fact caching is configured, Ansible may reuse cached values until they expire or are refreshed. Even freshly gathered facts describe the host at gather time and can become outdated after changes during a long-running workflow. Understand the play's fact-gathering and cache configuration before relying on a value.
</details>
